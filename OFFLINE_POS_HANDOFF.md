# Innova365 POS — техническая передача контекста

**Дата фиксации:** 29 октября 2026 года  
**Статус:** рабочее дерево содержит автономную кассу и незавершённое исправление маршрута печати. Готовую к установке новую версию после этого исправления ещё не выпускали.

## 1. Зачем существует этот документ

Этот файл предназначен следующему разработчику или ИИ-агенту, который продолжит работу прямо в текущем репозитории. Он описывает требования владельца проекта, подтверждённое состояние кода, проверенные сценарии и границы результата. Описание сделано по фактическому состоянию рабочего дерева; прежние ответы в чате нельзя считать подтверждением готовности продукта.

**Главное требование владельца:** кассовая программа должна выполнять всю ежедневную работу на компьютере заведения, включая вход, заказы, оплату, склад, отчёты и печать. Интернет и глобальный сервер не должны участвовать в обработке продажи. Когда связь появится, глобальный сервер должен получать данные для отчётов Innova Office. Касса должна продолжать работать при отказе сервера.

Владелец выбрал Electron для настольного приложения. Важно точно называть результат: сейчас это **локально работающий Electron-клиент с упакованным React-интерфейсом и локальными службами**, а не интерфейс на нативных Windows-контролах. Нативный доступ нужен прежде всего к печати и окружению Windows. Если под «полностью нативным» далее будет подразумеваться замена React-интерфейса на WinUI/WPF/Flutter, это отдельная большая переделка, которая в текущем коде не выполнена.

## 2. Обязательные свойства целевой системы

1. Локальная БД на кассовом ПК является источником истины для продаж, заказов, смен, остатков и сотрудников этого заведения.
2. Создание заказа и подтверждение оплаты не должны ждать сети или ответа `innova365.kz`.
3. Один Windows-установщик EXE должен содержать интерфейс, backend, его зависимости, бинарники и DLL локальной БД, а также подготовленные данные конкретного заведения. Отдельная установка Node.js или PostgreSQL не должна требоваться.
4. Кассовый чек и отчёт должны отправляться на принтер **этого компьютера** через Windows или другой контролируемый локальный транспорт. Приложение не должно молча выбирать постороннее USB-устройство.
5. Данные для офиса должны передаваться на сервер после восстановления связи с повтором и защитой от дублей. Ошибка передачи не блокирует кассу.
6. Установщик одного кафе не должен содержать данные другого кафе. Секреты, хеши паролей и дамп должны обрабатываться как закрытые данные.
7. Для оператора интерфейс должен быть понятным без знания терминов разработчика; ранее пользователь просил убрать служебные объяснения с экранов входа и настроек.

## 4. Фактическая архитектура автономной сборки

```text
Electron.exe
 ├─ BrowserWindow: упакованный React UI
 │    └─ http://127.0.0.1:<случайный порт>/
 │         └─ /api/* → Express API на 127.0.0.1:<другой порт>
 ├─ Express API, запущенный как дочерний процесс Electron/Node
 │    └─ Prisma → PostgreSQL на 127.0.0.1:<третий порт>
 ├─ переносимые бинарники PostgreSQL 16 для Windows x64
 └─ мост Electron → системные принтеры Windows
```

Код запуска: `native-innova365/src/main.js`, `src/paths.js`, `src/local-ui.js`, `lib/local-runtime.js`. Упаковка описана в `native-innova365/package.json` через `electron-builder` и `extraResources`.

При наличии упакованного `offline-manifest.json` либо переменной `INNOVA_OFFLINE_POS=1` `main.js` выбирает офлайн-режим. Он запускает локальную БД и API, затем поднимает локальный шлюз UI. В этом режиме экран активации сервера пропускается. Запросы интерфейса к `/api` идут в локальный Express; обычная кассовая операция не должна идти к `innova365.kz`.

`lib/local-runtime.js` на первом запуске создаёт кластер `initdb`, генерирует случайные пароль БД и JWT-секреты, восстанавливает подготовленный SQL-дамп и выполняет `prisma migrate deploy`. PostgreSQL, API и шлюз UI слушают только `127.0.0.1`. Дочерний backend запускается через `ELECTRON_RUN_AS_NODE=1`. Данные лежат в Electron `userData/offline/`, а не рядом с EXE. При штатном выходе выполняется `pg_dump -Fc`; сохраняются семь последних резервных копий.

В `backend/src/server.ts` для локального процесса предусмотрено `HOST=127.0.0.1`. В `backend/src/controllers/auth.controller.ts` есть ветка `INNOVA_LOCAL_MODE=1`: PIN сверяется с локальными bcrypt-хешами. Это необходимо, потому что `pinKey` из прежней серверной БД был связан с другим секретом. Обычный серверный путь входа остаётся отдельным.

**Существенное ограничение:** синхронизация автономной БД с глобальным сервером **не реализована**. Поэтому действующие отчёты Innova Office не получают новые локальные продажи автоматически. Прежнее утверждение, что система уже полностью соответствует всей целевой архитектуре, было ошибочным.

## 6. Печать: подтверждённый баг и текущая правка

На последнем скриншоте приложение показало ошибку:

```text
Не удалось напечатать — no bulk-out endpoint (not a printer interface)
```

Причина по коду: `PrintPanel` мог автоматически выбрать ранее сохранённый WebUSB-принтер раньше системного принтера Windows. USB-устройство было доступно браузерному API, но в выбранном интерфейсе не было bulk-OUT endpoint для печати. Это ошибка выбора транспорта; такой результат ничего не говорит о работоспособности самого принтера.

Исправления **уже внесены в рабочее дерево, но ещё не выпущены в новом EXE**:

- `frontend/src/components/shared/PrintPanel.tsx`: при наличии нативного моста Electron выбирается сохранённая очередь Windows, затем физический принтер Windows по умолчанию либо доступный физический принтер; WebUSB и серверные варианты не предлагаются для установленного Electron. Если подходящей очереди нет, остаётся системный диалог.
- `frontend/src/lib/printClient.ts`: быстрая печать заказа и печать после оплаты в Electron открывают печатный документ с автопечатью через нативный маршрут, а не сохранённую WebUSB-настройку.
- `native-innova365/src/session-setup.js`: в локальном режиме WebUSB-разрешение блокируется.
- `frontend/src/hooks/useRealtime.ts`: упакованная локальная касса не подключает внешнюю Supabase Realtime-подписку.

Нативный мост: `native-innova365/src/preload.js` → `src/ipc.js` (`web:systemPrinters`, `web:printDocument`) → `src/print-silent.js` (`webContents.print` через выбранную очередь Windows). Путь ESC/POS RAW через `lib/rawprint.js` и встроенный агент также есть, но его результат «Windows приняла задание» **не подтверждает**, что чек физически вышел целиком.

Из прошлой диагностики в другом заведении: принтер был подключён по USB и виден Windows как очередь `check`, порт `USB001`, драйвер `80Normal`; пользователь называл оборудование POS-80. Тестовая страница Windows и самотест устройства печатались. Отправка RAW-задания через агент возвращала `ok: true`, но бумага не выходила. Позже после перезапуска `Spooler` и теста Windows бумага выходила, однако печать из приложения всё ещё была проблемной. Это подтверждает, что нельзя считать ответ драйвера окончательным тестом продукта. Физическая проверка нового Electron-маршрута на этом устройстве **ещё не проведена**.

При проверке на кассе нужны: полный чек с несколькими строками, кириллица, знак тенге, QR, конец документа и отрез. Отдельно проверить 58/80/90 мм и длинный итоговый отчёт. Не подключать WebUSB через Zadig к уже работающему системному принтеру ради обхода этой ошибки: это может заменить обычный драйвер Windows.

## 9. Незавершённые архитектурные задачи

### 9.1. Синхронизация с Innova Office

Сейчас Office читает центральные `public`-таблицы, а автономная касса пишет в локальные. Это разные базы. Простая отправка только суммы дня не заменит все существующие отчёты Office, поскольку часть кода использует позиции заказа, методы оплаты, категории, сотрудников и другие связи.

Нужен отдельный проект решения:

1. Определить, какие отчёты Office должны работать на синхронизированных данных и какая детализация для них нужна.
2. Записывать события либо снимки продаж в локальную долговечную очередь **в той же транзакции**, что и бизнес-изменение. У каждого события должны быть `restaurantId`, `deviceId`, уникальный `eventId` и версия формата.
3. Создать на сервере аутентифицированный endpoint приёма, который проверяет принадлежность устройству и заведению, принимает повторы идемпотентно и хранит только нужные для Office данные.
4. Отправлять очередь в фоне с ограничением размера пакета и повтором после обрыва. Не блокировать продажу и не скрывать длительную ошибку синхронизации от владельца.
5. Показывать Office время последнего обновления данных и различать «нет продаж» от «касса не синхронизировалась».
6. Проверить дубли, пересортировку событий, восстановление из резервной копии, смену кассового ПК и две кассы одного заведения.

Механизм авторизации автономной кассы на сервере ещё не сделан. Имеющаяся онлайн-активация Electron существует, но офлайн-ветка сейчас её обходит; нельзя объявлять её готовым безопасным каналом синхронизации.

### 9.2. Месячная подписка

В серверном backend есть данные оплаченного периода и журнал продлений; в интерфейсе показывается статус. Автономный подтверждённый документ лицензии, правила работы при длительном отсутствии сети и безопасное продление локальной установки ещё не реализованы. Оплата не должна неожиданно остановить кассу посреди смены.

### 9.3. Многотерминальная работа

Две независимые установки сейчас имеют две независимые БД. Автоматического объединения заказов нет. Если нескольким устройствам нужен один зал, следует выбрать один локальный узел или отдельный протокол синхронизации и явно определить конфликты редактирования заказа. Не устанавливать две самостоятельные копии, предполагая, что столы и платежи появятся на обеих автоматически.

### 9.4. Резервное копирование и восстановление

Штатный выход создаёт `pg_dump`, но нужна процедура восстановления, тест на обрыв питания, контроль места на диске и проверка копий. При переносе кассы требуется сохранить БД или резервную копию **вместе с** `local-secrets.json`. Удаление приложения не должно случайно уничтожать данные продаж.

Ожидаемый путь новой сборки: `native-innova365/dist/Innova365-Setup-1.2.0-beta.2.exe`. До появления файла и проверки времени его создания нельзя ссылаться на него как на готовый результат.

Для локальной проверки работы БД использовать **новую пустую тестовую папку**, например:

```powershell
Set-Location 'C:\Users\BAGDAULET-KOPTILEU\Desktop\IIKOProject\native-innova365'
node tools/smoke-local-runtime.js '..\.scratch\offline-smoke-next'
```

Не передавать путь к действующей пользовательской БД: тест специально изменяет пароль и PIN одного владельца в своей тестовой копии, создаёт и оплачивает тестовый заказ.

## 12. Критерии приёмки перед новым кафе

- Установить один EXE на чистый Windows x64 без отдельно установленного Node.js и PostgreSQL; убедиться, что выбран дамп **нужного** кафе.
- Отключить интернет до запуска. Войти под сотрудником, открыть стол, добавить позиции, отправить заказ на кухню, принять оплату, открыть локальный отчёт. Проверить сохранение после перезапуска.
- На принтере Windows, выбранном по имени, напечатать полный короткий и длинный чек, затем итоговый отчёт. Проверить читаемую кириллицу, знак валюты, QR, таблицы, отсутствие обрезки и отрез бумаги. Ошибка `no bulk-out endpoint` не должна появляться.
- Проверить, что при отключённом сервере продажа завершается с корректным номером и суммой; после восстановления сети данные доходят в Office ровно один раз **после реализации синхронизации**.
- Сверить локальную кассу и Office по количеству оплаченных заказов, выручке, способам оплаты, сотрудникам и возвратам. Office должен показывать давность синхронизации.
- Проверить резервную копию и восстановление на другом тестовом ПК; не использовать действующую БД кафе для разрушительных тестов.

## 13. Требования к коммуникации и развёртыванию

Владелец неоднократно просил точные команды и не хочет длинных цепочек `scp && ssh && docker compose` в одном вызове PowerShell. Если потребуется серверный патч, давать отдельно: команду архивации и `scp` на Windows, затем команду `ssh`, затем команды внутри Ubuntu. Не включать `.env.example` вместо рабочего `.env` и не загружать лишние проекты. Для локального EXE серверный Docker вообще не требуется.

При отчёте о результате разделять три статуса: **код изменён**, **пакет собран**, **проверено на реальном принтере**. Никогда не превращать успешный ответ API или очереди Windows в утверждение, что физический чек напечатан. Не называть текущую автономную кассу завершённой интеграцией с Office, пока нет проверенной синхронизации.
