# QA кассового приложения Innova365 — 25.10.2026

## Объект и подход

Проверена **локальная** Docker-сборка проекта `iikoproject` по адресу `http://localhost:8080` с API `http://localhost:3001`. Сервер `194.32.142.75` и физический Xprinter в эту проверку не входили. Office, DB Admin и Electron-клиент не тестировались как отдельные продукты.

Порядок проверки и исправления:

1. Снять состояние контейнеров и сохранить локальную резервную копию БД до миграций.
2. Воспроизвести реальные операции в браузере под администратором, официантом, поваром и кассиром.
3. Сверить изменения заказа с кухней, оплатой, столами, складом, чеком и отчётами.
4. Проверить API отдельно: отсутствие авторизации, ограничения ролей, ошибки ввода и поиск с пагинацией.
5. Исправить воспроизводимые дефекты, пересобрать только backend/frontend, повторить ключевые сценарии и зафиксировать ограничения.

## API и автоматические проверки

- Сборка backend TypeScript и frontend Vite/TypeScript прошла. `npm test` backend: **11/11** тестов, включая списание брутто, возврат при отмене, защиту занятого стола, смену роли после refresh, конфликт статусов, актёра кухни, оплату и таблицы кассового отчёта.
- Проверены ответы 401/403 для доступа без роли, 400 для неверного периода отчётов и неверной пагинации, 200 для разрешённых операций. Официант при `PATCH /pedidos/:id/pago` получает 403.
- Сборка контейнеров backend/frontend завершилась успешно; применены миграции техкарт, кассового чека и исполнителя кухни. Office не пересобирался.

## Оставшиеся риски и границы проверки

1. **Xprinter не подключён.** Подтверждены только HTML-предпросмотр, выбор 58/80 мм и маршрут кнопки. Фактическую печать, кодировку кириллицы, обрезку ленты, USB/IP/print-agent и поведение после потери связи надо проверить в офисе на конкретном устройстве.
2. **Учет остатков не блокирует продажу при нуле.** Например, техкарта Coca-Cola 1,5 л показывает 0 доступных порций, но позиция остаётся в меню. Текущая логика списания может увести остаток в минус. Нужное правило продажи при недостатке склада необходимо определить с владельцем; до этого целесообразно как минимум показывать предупреждение кассиру и явно отмечать отрицательные остатки.
3. **В базе есть исторические тестовые цены.** Месячный отчёт содержит, например, 20 штук сета «Праздничный» на 1040 ₸. Эти данные требуют отдельной сверки перед управленческим использованием отчёта; текущие агрегации арифметически согласованы, но достоверность исторических цен не подтверждена.
4. **Проверка не была исчерпывающей по устройствам и интеграциям.** Отдельно нужны: мобильные/планшетные размеры, реальные сетевые обрывы, параллельные заказы несколькими сотрудниками, печать после перезапуска Electron/агента, Office, DB Admin и серверное окружение Ubuntu.
5. **Тестовые данные остались в локальной БД.** Заказы №30132 (5100 ₸, наличные) и №30133 (700 ₸, карта) оплачены и отражены в выручке/движениях склада. Они не загружались на удалённый сервер. Удалять только сами строки заказов нельзя без согласованной коррекции оплат, остатков и журнала движений.

## Решение перед выкладкой

Локальные основные сценарии работают после исправлений. Для утверждения печати и выкладки нужен отдельный короткий приёмочный прогон в офисе: Xprinter 58/80 мм, заказ за столом и «С собой», отмена, печать чека и итогового отчёта, сверка суммы и остатков. На удалённый Ubuntu-сервер эта QA-проверка ничего не отправляла.
