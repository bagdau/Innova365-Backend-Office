# Innova365 POS: локальная работа и синхронизация

> Исторический план SQLite-прототипа. Актуальная сборка с локальным PostgreSQL описана в `OFFLINE_RELEASE.md`.

## Цель

Установленная касса принимает заказы, оплату, печатает чеки и строит кассовый отчёт без интернета. Сервер получает события продаж и телеметрию после восстановления связи. Интерфейс поставляется внутри установщика Electron; операционная база кассы находится на самом устройстве.

## Текущее состояние

- Electron 1.1.2 загружает интерфейс с `https://innova365.kz`; экспериментальный локальный интерфейс в 1.1.3-dev.0 пока направляет `/api` на тот же сервер и **не является офлайн-кассой**. Он включается только через `INNOVA_LOCAL_UI=1`.
- Действующий backend использует PostgreSQL через Prisma. Браузерный фронтенд вызывает примерно 80 маршрутов API. Прямое вложение SQL-файла в Electron не создаёт локальный API.
- Полученный дамп PostgreSQL 16.15 содержит схему `office` и POS-схему `public`. В POS-части: 1 ресторан, 12 пользователей, 16 категорий, 29 товаров, 2 заказа и **0 техкарт**. В дампе также есть сессии Office, записи активации и хеши учётных данных. Его нельзя распространять как общий установщик для разных кафе.
- Прототип импорта `node tools/import-catalog.js <dump.sql> <new-local-db.sqlite>` создаёт отдельную SQLite-базу каталога из дампа одного заведения. Он переносит ресторан, категории, товары, столы, ингредиенты и техкарты; учётные данные, старые заказы и служебные токены исключены. База каталога пока не подключена к рабочим операциям кассы.
- `lib/offline-sales.js` теперь хранит создание заказа, оплату и очередь событий в одной SQLite-транзакции. Повторный запрос с тем же ID не дублирует продажу, повторная оплата с другим ID отклоняется. Это пока ядро данных: локальный вход, API, склад, отчёт и обмен с сервером ещё не подключены.
- На сервере есть учёт оплаченного периода по заведению и неизменяемый журнал продлений. Владелец видит оставшиеся дни в «Настройки → Приложение», в том числе последний сохранённый статус без сети. Продление вносится оператором после подтверждения оплаты: `npm run billing:grant -- <restaurant-id> <months> <unique-payment-reference>`. Это пока **не платёжный шлюз** и не механизм блокировки кассы.

## Целевая схема

1. Локальная SQLite-база на кассовом ПК в пользовательских данных приложения. Режим WAL, транзакции для заказа и оплаты, регулярная локальная резервная копия. Данные каждого заведения изолированы.
2. Импорт конкретного заведения из дампа при настройке кассы: ресторан, меню, цены, столы, остатки, техкарты и нужные сотрудники. Сессии, токены активации, журнал печати, старые задания и ключи синхронизации не импортируются. Исторические заказы, если нужны, помечаются как уже учтённые и не попадают в очередь синхронизации.
3. Локальный API для входа, меню, столов, заказов, оплаты, склада, чеков и отчёта. Эти операции обращаются только к локальной БД. Электронное окно загружает упакованный интерфейс.
4. Каждое подтверждённое изменение одновременно записывается в бизнес-таблицы и локальную очередь `outbox` в одной транзакции. У события уникальные `deviceId`, `eventId` и последовательный номер. Повторная отправка не создаёт дубликат продажи на сервере.
5. Фоновый обмен выгружает события на сервер и показывает в кассе число неотправленных операций, время последней синхронизации и ошибку. Интернет или отказ сервера не блокирует продажу. Сервер используется для отчётов и телеметрии.
6. Если в кафе несколько терминалов, один локальный узел на кассовом ПК хранит рабочую базу; остальные устройства в этой локальной сети используют его API. Одновременное редактирование одного заказа требует отдельного правила конфликтов до ввода такого режима.
7. Печать работает отдельно от синхронизации. Ответ драйвера «задание принято» не считается подтверждением, что бумага вышла целиком; это проверяется на POS-80 физическим тестом.
8. Подписка оплачивается помесячно. Сервер хранит `paidUntil` и журнал продлений с уникальным номером платежа; повторное подтверждение одного платежа не добавляет второй месяц. Для офлайн-кассы нужен подписанный сервером документ о сроке доступа и оговорённый период без связи. До согласования тарифа, способа оплаты и правил просрочки таймер только информирует владельца и не останавливает продажи.

## Приёмочные сценарии перед установкой в кафе

- Первое подключение: импорт данных именно этого заведения, вход сотрудника, проверка локального меню и цен.
- Отключить интернет: открыть стол, добавить два блюда, принять оплату, распечатать полный чек, получить локальный итоговый отчёт.
- Перезапустить кассу без сети: заказ, оплата и номер чека остаются; повторная оплата не возникает.
- Вернуть интернет: очередь уходит на сервер один раз, суммы в отчёте совпадают с локальной кассой.
- Повторить с двумя кассами в одной локальной сети и отдельно проверить USB-принтер `check` с драйвером `80Normal`.

Никакой установщик 1.1.3-dev.0 не выпускается до выполнения этих сценариев.
